# The LLM630 behind a T-Embed (C-76)

*Researched 2026-10-07 from M5Stack's own source and documents: the StackFlow repository (the units' code and
`doc/projects_llm_framework_doc/`), its OpenAI plugin, the M5Module-LLM Arduino library, the LLM630 product page and
its schematic (K143, 2024-11-29), and LilyGO's T-Embed-CC1101 repository. What it takes to make the LLM630 the
handheld's offline brain. Nothing here has been run on the bench yet; what was read only in code says so.*

## How a microcontroller talks to it

StackFlow is a set of **units** (one Linux service each: `llm`, `whisper`, `asr`, `kws`, `vad`, `melotts`, `tts`,
`audio`, `vlm`, `yolo`, `camera`) behind one front door, `llm-sys`. The front door listens on **a UART at 115200 8N1**
and on **TCP port 10001** (enabled by default in `main_sys`). **The same JSON goes over either.** The sys unit finds each
object by its braces, so no delimiter is needed; replies come back one JSON object at a time.

A request names the unit, the action and what the data is:

```json
{"request_id":"1","work_id":"llm","action":"setup","object":"llm.setup",
 "data":{"model":"qwen2.5-0.5B-prefill-20e","response_format":"llm.utf-8.stream","input":"llm.utf-8",
         "enoutput":true,"max_token_len":256,"prompt":"You are ..."}}
```

`setup` answers with the instance's id (`"work_id":"llm.1002"`, `error.code` 0 is success); every later call uses that
id. **`inference`** sends it data, either whole (`"object":"llm.utf-8","data":"hello"`) or in pieces
(`"object":"llm.utf-8.stream","data":{"delta":"hel","index":0,"finish":false}`). A streaming answer comes back the same
way, one `delta` at a time until `"finish":true`. **`exit`** frees the unit; `link`/`unlink` chain one unit's output into
another's input on the board; `taskinfo` reports state; `sys` has `uartsetup` (baud) and others.

**The `object` string is the format.** The units read it word by word: `stream` means pieces to reassemble by `index`,
`base64` means decode it, `wav` means strip the header. So `whisper.wav.stream.base64` is a WAV, base64-encoded, sent
in pieces.

## What it can run

| unit | apt package (models) | what |
|---|---|---|
| llm | `llm-llm` (`llm-model-qwen2.5-0.5B-prefill-20e`, `-qwen2.5-0.5B-p256-ax630c`, `-qwen2.5-0.5B-Int4-ax630c`, `-qwen3-0.6B-ax630c`, `-llama3.2-1B-prefill-ax630c`, `-qwen2.5-1.5B-ax630c`, `-qwen2.5-1.5B-Int4-ax630c`, `-deepseek-r1-1.5B-ax630c`, ...) | text in, text out, streamed |
| whisper | `llm-whisper` (`-whisper-tiny`, `-base`, `-small`) | speech to text, a whole utterance at once |
| asr | `llm-asr` (sherpa streaming zipformer, sense-voice-small) | speech to text, streaming |
| kws, vad | `llm-kws`, `llm-vad` (silero) | wake word, voice activity -- not needed for push to talk |
| melotts | `llm-melotts` (`-melotts-en-us`, `-en-default`, `-en-br`, `-en-au`, `-en-india`, `-es-es`, `-ja-jp`, `-zh-cn`) | text to speech on the NPU |
| tts | `llm-tts` (`single-speaker-english-fast`) | a lighter, plainer voice |
| openai-api | `llm-openai-api` | an OpenAI-style HTTP server on **port 8000** over the same units |

Installed from M5Stack's apt repository (`repo.llm.m5stack.com`, `jammy ax630c`): `lib-llm` and `llm-sys` first, then
any unit and model. M5's published speeds on the AX630C (context 128): **Qwen2.5-0.5B 10.3 tokens/s, first token
0.36 s** (its W4A16 build 37 tokens/s, 0.14 s); Qwen3-0.6B 10.3; Llama 3.2 1B 4.5 (0.89 s); Qwen2.5-1.5B 3.6 (3.1 s;
4.6 at W4A16). At 256 tokens of context the first token takes about three times as long. **No timings are published
for whisper or melotts**: measure them.

**Speech to text takes the host's audio: verified in code.** The whisper unit, set up with an input naming itself,
listens for `inference` data instead of the board's microphone, decodes base64, strips a WAV header and transcribes
the whole buffer; the sherpa `asr` unit does the same. M5's own OpenAI plugin does exactly this: it sets whisper up with
`"input":"whisper.wav.stream.base64"` and sends a WAV in 4,096-character pieces as `asr.wav.stream.base64` with
`delta`/`index`/`finish`. Whisper expects **16 kHz, 16-bit mono** -- what the T-Embed already records (`talk.cpp`).
**The LLM630 has no microphone in any case** (a 5-pin MIC/SPK header with an NS4150B amplifier, nothing on it), so
this is the only way in.

**Text to speech returns audio to the host: verified in code.** With a `response_format` that does not contain `sys`,
melotts sends its audio back instead of playing it: **raw 16-bit PCM at 16 kHz mono** (the model's 44.1 kHz resampled to
the config's `audio_rate` 16000), base64. That is what `soundPcm()` plays. **Ask for the stream form** --
`"response_format":"pcm.stream.base64"`, as M5's plugin does: melotts speaks a sentence at a time, and the non-stream
form sends only on the last sentence, so a several-sentence answer would come back as its last sentence alone (read in
`main_melotts`, not run). It is one stock voice per language, not the INDEX voice.

## Joining it to a T-Embed

**The LLM630's ports** (from its schematic): PortC, the blue Grove, is **GND, 5 V, TXD, RXD** (net `TRM_TXD/RXD`,
straight to the AX630C module, no level shifter); PortA, the red Grove, is the board's **own system I2C** (its charger,
gauge and IO expander), with 2.2 kΩ pull-ups. **The power pin on both is `SOC_VIN`, the output of a 5.1 V boost
converter** (FP6276; 0.6 V reference, 75k/10k divider) fed from USB or the battery. Two USB-C: **J5 is power in plus
the CH9102 debug console**; **J4 is USB 2.0 OTG**, and in host mode it switches `SOC_VIN` out onto its VBUS. A 2-pin
1.25 mm battery socket (3.7 V) with an AW32001 charger and a BQ27220 gauge; 5 V 2 A in. **Power draw is not published**
(the stacking LLM Module is quoted at about 0.5 W idle, 1.5 W working; budget more for the LLM630's Ethernet and Wi-Fi).

**Unverified**: PortC's logic level (3.3 V by every sign -- no shifter, and the same module talks to 3.3 V Cores --
measure it before wiring), and whether StackFlow's UART (`/dev/ttyS1` in `main_sys`) is PortC on this board (check
with `ls /dev/ttyS*` and a loopback).

**The T-Embed CC1101 has two 4-pin headers on its back** (LilyGO's README picture): **UART -- RXD IO44, TXD IO43, 3V3,
GND** and **I2C -- IO8, IO18, 3V3, GND**. IO43/44 are UART0, free in this firmware (`Serial` is USB-CDC,
`ARDUINO_USB_CDC_ON_BOOT=1`), so `Serial1.begin(115200, SERIAL_8N1, 44, 43)` reaches PortC: **TX to RX, RX to TX, GND to
GND, and the power wire left off** -- PortC's pin is 5 V, the T-Embed's is a 3.3 V rail. Two catches: the ESP32-S3's
boot ROM prints on IO43 at reset (the sys unit ignores what is not JSON), and **the CC1101 PLUS uses IO43/44 for its
nRF24**. The plain T-Embed's expansion pins were not checked. The connector type was not stated: measure the pitch.

**Speed is the problem with the UART.** An 8-second recording is 256 KB, 342 KB as base64: **about 30 s at 115200**,
and a 10-second answer's audio about 37 s back. Text is fine at 115200; audio needs `sys.uartsetup` to 921600 or more
(**unverified** that the AX630C's UART and StackFlow take it; the library's `setBaudRate()` sends exactly this). Wi-Fi
or USB have no such limit.

## Recommended design

**One talk turn, offline**, with the T-Embed as the host (it holds the carried daemon, so it holds the character):

1. At start, set up three units once: `whisper` (`whisper-base`, `"input":"whisper.wav.stream.base64"`,
   `"response_format":"asr.utf-8"`), `llm` (Qwen2.5-0.5B, the daemon's character as `prompt`, `max_token_len` about 128,
   `llm.utf-8.stream`), `melotts` (`melotts-en-us`, `"input":"tts.utf-8"`, `pcm.stream.base64`).
2. Hold the dial: record as now (16 kHz WAV, up to 8 s). Let go: send it to whisper in pieces -> the words heard.
3. The words to the llm; show its deltas on the TALK screen as they arrive (the screen fills at about ten tokens/s).
4. The finished answer to melotts; play each returned piece as it comes (`soundPcm`).

`link` can chain whisper -> llm -> melotts on the board, but the host then cannot show the words heard or refuse an
empty one; chain by hand first. **Keep the character prompt short**: the first token's wait grows with it (0.36 s at
128 tokens, 1.1 s at 256), and the prefill models hold 128-256 tokens of context, not the server's long prompt.

**The link, in order of what to try:**

- **Wi-Fi TCP 10001 first** -- no wiring, and the same JSON. Offline means no internet, not no radio: the T-Embed can be
  the access point (ESP32-S3 soft-AP) and the LLM630 join it (`nmtui`), or both join one network. Whether the LLM630's
  ESP32-C6 can itself be an access point is unverified. A shortcut: `llm-openai-api` on port 8000
  (`/v1/audio/transcriptions` takes a WAV, `/v1/audio/speech` with `"response_format":"pcm"` returns 16 kHz PCM) is
  close to what `talk.cpp` already does over HTTP.
- **USB-C, T-Embed to the LLM630's OTG port** -- one cable, power and data: the LLM630 as host gives 5 V and sees the
  T-Embed as `/dev/ttyACM0`; a bridge on the LLM630 (`socat /dev/ttyACM0,raw,echo=0 TCP:127.0.0.1:10001`) carries the
  same JSON at full USB speed. **Unverified** that J4 sources power to a C-to-C device, and the T-Embed's charger would
  then charge its own cell from the LLM630's (up to its set current). It also takes the USB port the server link uses.
- **PortC UART** -- the simplest wiring and no radio, but text-speed until a higher baud is proven.

**On the bench, first**: (1) on the LLM630 over its console or SSH, install `llm-sys llm-llm llm-whisper llm-melotts`
and the three models; (2) from a laptop, `nc` to port 10001 and run one turn by hand with a WAV the T-Embed recorded --
time whisper, the llm and melotts separately; (3) measure the LLM630's draw idle and mid-turn, on battery; (4) the
T-Embed over Wi-Fi; then (5) the wired link.

## What the firmware does now (2026-10-07, built, not yet run on an LLM630)

`firmware/esp32/src/brain.cpp` is the client above: **when no server answers a talk turn, it goes to the LLM630**. It
sets up `whisper` (whisper-base, host audio), `llm` (Qwen2.5-0.5B-prefill-20e, a two-line character prompt) and
`melotts` (melotts-en-us, `pcm.stream.base64`) once, then sends the recording in 4,096-character pieces, shows the words
heard and the answer as it streams, and plays each piece of voice as it arrives. **Choose the link down the cable**
(from the computer, while the board is plugged in):

```
BRAIN tcp 192.168.4.2:10001     the LLM630 on the network (port 10001 by default)
BRAIN uart                      the CC1101's back header: RX 44, TX 43
BRAIN off
```

The choice is kept in the board's flash. Every name in the messages (`asr.wav.stream.base64`, the model names) is from
M5's code, not from a run: the first bench session is where they are checked.

## Open questions for the user

- **Which link**: Wi-Fi (no wires, the radio on), USB-C (one cable, power both ways), or PortC (three wires, slow audio)?
- **Does the LLM630 ride on its own battery**, or power the T-Embed (USB OTG or a 5 V line into the T-Embed's USB), or
  the reverse? A shared battery needs the boost's limits checked.
- **Which model holds a daemon's character best** in a few seconds a turn: Qwen2.5-0.5B (fast) or a 1-1.5B (half speed)?
- **The voice**: melotts' stock English voice offline, against the INDEX voice when online -- or the online one always,
  and the LLM630 only when there is no network?
- **Which T-Embed** carries it: the CC1101 has the UART header; the PLUS has those pins taken; the plain T-Embed is
  unchecked.
